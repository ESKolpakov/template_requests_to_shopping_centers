# ТЗ: Windows-приложение для генерации писем в УК ТЦ

> Копия исходного технического задания, положенного в основу приложения.
> Значения по умолчанию для полей «Исполнитель» / «Телефон исполнителя» /
> «Подписант» из раздела 7 в этой копии заменены плейсхолдерами — в
> оригинальном ТЗ там указаны реальные ФИО и рабочий телефон конкретного
> сотрudника; эти персональные данные не публикуются в открытом
> репозитории (см. README.md, раздел «Приватность»). В самом приложении
> эти поля пустые по умолчанию и заполняются пользователем один раз в
> разделе «Настройки» — оттуда они сохраняются только локально.

## 0. Контекст и цель

ГБУ «МКМЦН» рассылает в управляющие компании (УК) торговых центров (ТЦ) типовые письма
«Об оказании содействия» с просьбой предоставить сведения о хозяйствующих субъектах
для целей исчисления торгового сбора. Сейчас письма готовятся вручную в Word: сотрудник
копирует бланк, вручную выравнивает адресный блок пробелами, ищет данные об УК по
каждому ТЦ и вставляет таблицу объектов из Excel-выгрузки.

Нужно приложение под Windows (лёгкое, локальное), которое:
1. Принимает на вход стандартную (без предобработки) Excel-выгрузку объектов торговли
   и таблицу контактов УК/ТЦ.
2. Автоматически формирует пакет писем в формате .docx — по одному письму на адрес
   здания — с точным сохранением бланка, шрифта, вёрстки и стиля исходных писем.
3. Умеет автоматически доразведывать данные об УК через ЕГРЮЛ (полуавтоматически,
   с участием человека на этапе капчи).
4. Ведёт реестр результатов генерации и позволяет донастраивать переменные поля
   (даты, исполнитель, подписант) перед каждым запуском.

Примеры файлов (9 писем-образцов, выгрузка «Реестр ТО», справочник УК/ТЦ,
3 PDF-выписки ЕГРЮЛ) в открытый репозиторий не публикуются — все они
содержат персональные данные (ФИО, ИНН, телефоны, адреса) реальных людей
и организаций. См. README.md, раздел «Как проверить на своих данных».

## 1. Общая архитектура

- Целевая платформа: Windows, локальное автономное приложение (может быть собрано
  в единый .exe через PyInstaller или аналог — на усмотрение исполнителя, но без
  требования устанавливать Python на компьютер пользователя).
- Стек по умолчанию: Python + `python-docx` (генерация .docx) + `openpyxl`/`pandas`
  (чтение Excel) + GUI на tkinter или PyQt (на усмотрение — важна простота
  установки и лёгкость интерфейса, а не конкретный фреймворк).
- Приложение полностью работает офлайн, **кроме** одного полуавтоматического шага —
  открытия страницы egrul.nalog.ru в браузере для скачивания выписки (см. раздел 6).
- Никаких данных никуда не отправляется автоматически — все проверки по ИНН
  инициируются пользователем вручную по каждому конкретному ТЦ.

### 1.1. Главное меню / структура приложения

Приложение должно иметь понятную навигацию (вкладки или пункты меню):

1. **Шаблоны** — загрузка и управление шаблоном(ами) письма (см. раздел 2).
2. **Источники данных** — загрузка Excel с объектами торговли и Excel/таблицы
   контактов УК ТЦ (см. раздел 3).
3. **Настройки** — исполнитель, телефон, подписант, дата отсчёта срока,
   длительность срока (см. раздел 7).
4. **Проверка по ЕГРЮЛ** — ручной/полуавтоматический модуль доразведки данных
   об УК (см. раздел 6).
5. **Генерация писем** — запуск формирования пакета писем + реестр результатов
   (см. раздел 8).

## 2. Управление шаблонами (загружаются через меню)

- Шаблон письма (бланк, шапка ГБУ «МКМЦН», стандартный текст, блок подписи,
  таблица-приложение, футер с пометкой про заполнение) должен быть **загружаемым
  файлом**, а не зашитым намертво в код — это позволит менять шаблон в будущем
  без переписывания приложения.
- Реализация: пользователь через меню «Шаблоны» загружает эталонный .docx
  (можно взять любой файл из `examples/letters/` как основу для первой версии
  шаблона), внутри которого выделены переменные зоны (плейсхолдеры).
- Плейсхолдеры на основе анализа образцов (см. раздел 5 для полной семантики):
  - `{{RECIPIENT_BLOCK}}` — весь адресный блок (должность/УК/ФИО/адрес или
    «Администрация торгового центра» + адрес)
  - `{{GREETING}}` — строка «Уважаемый/Уважаемая Имя Отчество!» (пустая строка,
    если письмо обезличенное)
  - `{{TC_NAME}}` — название торгового центра
  - `{{TC_ADDRESS}}` — адрес торгового центра (без «комната ...»)
  - `{{DEADLINE_DATE}}` — рассчитанная дата срока предоставления информации
  - `{{SUBJECT_WORD_FORM}}` — форма единственного/множественного числа
    («хозяйствующем субъекте»/«хозяйствующих субъектах», «объекта»/«объектов»,
    «деятельность...осуществлял»/«...осуществляли» — см. пример письма на
    ул. Матвеевская, д.2, где два ХС в одном ТЦ)
  - `{{EXECUTOR_NAME}}`, `{{EXECUTOR_PHONE}}` — исполнитель и телефон
  - `{{SIGNATORY_NAME}}` — подписант (по умолчанию «Заместитель директора
    С.В.Вихирева», с возможностью подмены)
  - `{{OBJECTS_TABLE}}` — таблица объектов торговли (переменное число строк)
- Само оформление (шрифты, отступы, стили таблицы, футер с примечанием
  про заполнение от руки, «М.П.» и т.д.) **не меняется** — копируется из
  шаблона 1-в-1 средствами python-docx (см. раздел 5.5 про технические
  требования к вёрстке).
- Приложение должно позволять заменить шаблон новым файлом в любой момент
  (например, если поменяется официальный бланк ГБУ «МКМЦН»).

## 3. Источники данных (загружаются раздельно через меню)

Оба источника загружаются **независимо друг от друга**, в любом порядке,
и могут обновляться/перезагружаться в любой момент — они не «зашиты» в
приложение.

### 3.1. Выгрузка объектов торговли («Реестр ТО» из АИС ОПН)

- Файл загружается **как есть**, без какой-либо ручной предобработки —
  см. пример `examples/excel/report_-_2026-08-11T165157_484.xlsx`.
- Структура: первая строка — заголовок отчёта («Реестр ТО (сформировано
  средствами АИС ОПН, ...)»), вторая строка — реальные заголовки столбцов,
  далее данные. Всего 56 столбцов, используются только следующие:

| Столбец в исходном файле | Назначение | Преобразование |
|---|---|---|
| № п/п | номер в таблице приложения | пересчитывается заново в рамках каждого письма (не сквозная нумерация исходника) |
| Наименование ТО | название объекта в таблице | **убрать всё содержимое в скобках** вместе со скобками, например: «Мастер ПОЛО (ТЦ до 14.08.2026)» → «Мастер ПОЛО»; «Двери Регионов (доп запрос на нов УК ТЦ до 14.08.2026)» → «Двери Регионов» |
| Хозяйствующий субъект | как есть | — |
| ИНН | как есть | — |
| Адрес ТО | адрес объекта; служит и для группировки, и для поля «Адрес» в таблице | из адреса убирается хвост «, комната ...» — то, что до него, это ключ группировки в одно письмо; часть после «комната» не используется (дублирует следующий столбец) |
| Этаж | как есть | — |
| № квартиры (офиса) | в письме подписывается «Помещение» | — |
| Дата последнего обхода/АБО | в письме подписывается «Дата сбора информации» | — |
| Системный идентификатор объекта | в письме подписывается «ID» | — |

- Остальные ~47 столбцов (статусы, кадастровые номера, площади, ФИО
  обходчика, суммы сбора и т.п.) **игнорируются полностью**, никуда не
  переносятся.
- **Группировка**: строки с одинаковым «зданием» (адрес до «, комната»)
  объединяются в одно письмо — таблица-приложение получает столько строк,
  сколько объектов в группе (см. пример письма на ул. Матвеевская, д.2,
  где два хозяйствующих субъекта относятся к одному объекту «Hatsun» —
  в оригинальном docx это отражено через `rowspan` на общих столбцах;
  при генерации через python-docx нужно воспроизвести объединение ячеек
  там, где значения одинаковы для нескольких строк одного объекта,
  как в образце).
- Столбец «ID» в исходной таблице (последний, «Торговая деятельность
  подтверждается/не подтверждается») в письмо **не переносится** — эта
  колонка в письме всегда оставляется пустой (заполняется от руки).

### 3.2. Справочник контактов УК/ТЦ

- Файл — как в примере `examples/excel/1_Актуально_2026_контакты_ТЦ_ДТиУ....xlsx`.
- Структура (лист «Лист 1», заголовки в строке 1): № п/п, Адрес/иные
  ориентиры расположения торгового объекта, Район, Административный
  округ г. Москвы, Наименование ТЦ, Предполагаемое количество торговых
  объектов, Организационно-правовая форма (код по ОКОПФ), Управляющая
  компания, ИНН управляющей компании, Руководитель управляющей компании,
  Телефон управляющей компании, Email управляющей компании, Дополнительная
  информация, ответ.
- Заполненность полей неоднородна: где-то заполнено всё, где-то — только
  ИНН, где-то — вообще ничего, кроме адреса/email.
- Сопоставление с адресом объекта из «Реестра ТО» — по нормализованному
  адресу (регистронезависимо, без «район X,», без лишних пробелов/запятых,
  унификация сокращений «ул.»/«улица», «д.»/«дом», «корп.»/«корпус»,
  «стр.»/«строение»). Реализовать нормализацию адреса как отдельную,
  переиспользуемую функцию — она понадобится и здесь, и в модуле ЕГРЮЛ,
  и в модуле группировки.
- **Справочник должен быть перезагружаемым** пользователем в любой момент —
  количество строк и их содержимое будут регулярно меняться (дополняться
  новыми ТЦ, обновляться контакты). Приложение не должно жёстко привязываться
  к структуре конкретного файла сверх состава столбцов, описанного выше.
- Встречаются «отменённые»/неактуальные записи-примечания (например,
  «ООО "Амистад" не является управляющей компанией торгового центра
  "Вектор"» в отдельной строке дополнительной информации) — такие строки
  не должны автоматически перекрывать корректную запись; при неоднозначности
  (несколько строк с одним адресом/ТЦ) — помечать адрес как «требует ручной
  проверки» (см. раздел 8).
- Отдельный edge-case: строки, где для одного адреса указано **два и более
  ИНН** (пример: Варшавское шоссе, 26с7 — ИНН 7718784153 и 7714469866).
  Такие строки **не автоматизируются** — по решению постановщика задачи
  (см. раздел 9), они просто помечаются в реестре как «требуется ручная
  проверка», без попытки алгоритмически выбрать/разделить письма.

## 4. Логика адресного блока и текста письма

### 4.1. Два варианта адресата

**A. Обезличенный** (нет данных об УК в справочнике и не запускали проверку
по ИНН, либо ИНН тоже нет):
```
Администрация торгового центра
<адрес ТЦ>
```
Приветствия «Уважаемый...» в тексте письма в этом случае нет (см. примеры
писем на пр-т Мира и 9-ю Парковую).

**B. Персональный** (есть данные из справочника или из выписки ЕГРЮЛ):
```
<Должность, например «Генеральному директору» или «Директору»>
<Организационно-правовая форма + название, например «ООО «АКТИВО-ИНВЕСТ»»>
<Инициалы.Фамилия в дательном падеже, например «С.М.Лекомцевой»>
<юридический адрес>
```
и в теле письма — строка `Уважаемый/Уважаемая <Имя> <Отчество>!` (в
именительном падеже; см. пример: адресный блок — «С.М.Лекомцевой» (дательный),
приветствие — «Уважаемая Светлана Михайловна!» (именительный)).

- Должность («Генеральному директору», «Директору», «ИП» и т.п.) берётся
  из справочника (поле «Организационно-правовая форма») или из выписки
  ЕГРЮЛ (поле «Должность» в блоке «Сведения о лице, имеющем право без
  доверенности действовать от имени юридического лица»); формулировка
  должности в письме должна склоняться в дательный падеж
  («ГЕНЕРАЛЬНЫЙ ДИРЕКТОР» → «Генеральному директору»). Обеспечить словарь
  типовых должностей с готовыми дательными формами (генеральный директор,
  директор, ИП) + запасной вариант «Руководителю» для нераспознанных.
- «Уважаемый»/«Уважаемая» определяется по полю «Пол» из выписки ЕГРЮЛ,
  если оно есть; если данные пришли из справочника без явного пола — определять
  по окончанию отчества (авто, с возможностью ручной правки в интерфейсе
  перед сохранением письма).
- Склонение ФИО в дательный падеж для адресного блока — реализовать через
  доступную библиотеку морфологии (например, pymorphy2/pymorphy3), с
  пониманием, что на редких/иностранных ФИО (например, «Гулиев Гулам Билал
  Оглы») склонение может ошибаться — в этом случае приложение должно
  показать результат склонения пользователю на экране предпросмотра письма
  для ручной проверки/правки перед сохранением, а не сохранять втихую.

### 4.2. Единственное/множественное число в теле письма

Если в письме один хозяйствующий субъект — используются формы:
«осуществлял», «хозяйствующем субъекте», «объекта», «правоустанавливающих
документов (...) торгового объекта».

Если несколько (см. образец «ул. Матвеевская, д.2» с двумя ХС) — формы:
«осуществляли», «хозяйствующих субъектах», «объектов», «...торговых
объектов». Сравнить оба образца письма построчно, чтобы увидеть все места
замены множественного числа, и реализовать как условную подстановку по
числу строк в таблице-приложении.

### 4.3. Срок предоставления информации (дата)

- Расчёт: **дата формирования письма + 14 календарных дней**, затем —
  если результат выпадает на субботу/воскресенье или на праздничный
  день — сдвиг на ближайший следующий рабочий день.
- «Дата формирования письма» = стартовая дата, выбираемая пользователем
  в интерфейсе перед генерацией пакета писем (по умолчанию — сегодняшняя
  дата на момент запуска, но должна быть редактируемой, чтобы можно было,
  например, готовить письма в пятницу с расчётом даты от понедельника).
- Праздничные дни: перечень официальных нерабочих праздничных дней РФ
  меняется по годам и переносится отдельными постановлениями правительства
  (в отличие от фиксированных дат). Реализовать как **редактируемый список
  праздничных/нерабочих дат** (хранится в конфиге приложения, доступен для
  правки пользователем в настройках), а не как жёстко зашитый в код список —
  это единственный практичный способ, чтобы приложение не «сломалось» с
  началом следующего года. Задать список с основными фиксированными
  российскими праздниками (1–8 января, 23 февраля, 8 марта, 1 и 9 мая,
  12 июня, 4 ноября) как значение по умолчанию, но дать пользователю
  возможность добавлять/убирать даты.

## 5. Формат таблицы объектов торговли (приложение к письму)

Столбцы (см. образцы — они идентичны во всех 9 письмах):

№ п/п | Наименование объекта | Хозяйствующий субъект | ИНН | Адрес | Этаж |
Помещение | Дата сбора информации | ID | Торговая деятельность
подтверждается/не подтверждается (всегда пусто, для рукописной отметки)

- Ширины столбцов и стили — как в образцах (см. `examples/letters/*.docx`,
  таблица `colgroup` внутри каждого файла задаёт относительные ширины).
- Если у одного «Наименования объекта» несколько хозяйствующих субъектов
  (несколько строк, использующих один и тот же объект/адрес/этаж/помещение/
  дату/ID), эти столбцы объединяются по вертикали (rowspan) — см. пример
  «ул. Матвеевская, д.2» (объект «Hatsun», два ХС — Гулиев Г.Б.О. и
  Шагорская Т.А. — общие Наименование объекта/Адрес/Этаж/Помещение/Дата/ID
  объединены, различаются только «Хозяйствующий субъект» и «ИНН»).
- После таблицы — неизменный текст: линии для рукописной подписи/печати,
  «(Должность) (Подпись) ФИО (дата)», «М.П.», и сноска про заполнение
  таблицы от руки (текст сноски копируется из образца дословно, без
  изменений).

### 5.1. Технические требования к вёрстке (python-docx)

- Использовать шаблон (см. раздел 2) как основу и заполнять его через
  редактирование XML (`unzip` → правка `word/document.xml` → `zip`) —
  это надёжнее, чем собирать документ с нуля через docx-js/python-docx
  API, потому что гарантирует пиксель-в-пиксель совпадение с образцом
  (шрифты, отступы, стили таблиц, футер).
- Адресный блок — реализован в образцах через невидимую двухколоночную
  таблицу (без границ). Сохранить этот же приём при автозаполнении —
  никаких пробелов для выравнивания.
- Обязательно провести визуальную проверку: после генерации сконвертировать
  .docx в PDF (LibreOffice headless) и отрендерить в изображение, визуально
  сверить с образцом (совпадение шрифта, отступов, положения таблиц).

## 6. Модуль проверки по ЕГРЮЛ (полуавтоматический)

- Условие запуска: у ТЦ нет (или не хватает) данных об УК в справочнике,
  но есть ИНН.
- Шаги:
  1. Приложение открывает браузер пользователя на `https://egrul.nalog.ru/index.html`
     с ИНН, подставленным в поле поиска (автозаполнение формы — не обход
     капчи).
  2. Пользователь вручную проходит капчу, находит организацию, нажимает
     «Получить выписку» — сайт формирует PDF-файл, подписанный ЭЦП ФНС
     (см. примеры в `examples/egrul_pdfs/`).
  3. Пользователь либо вручную указывает скачанный файл в приложении, либо
     приложение отслеживает папку загрузок браузера по умолчанию и находит
     самый свежий PDF, подходящий по ИНН в имени файла (в примерах имя файла
     содержит ОГРН и таймстамп — при парсинге стоит свериться по ИНН внутри
     самого PDF, а не полагаться только на имя файла).
  4. Приложение парсит PDF (текстовый слой, не OCR) и извлекает:
     - Полное/сокращённое наименование организации (пункты «Полное
       наименование на русском языке» / «Сокращенное наименование...»)
     - Юридический адрес (пункт «Адрес юридического лица»)
     - Блок «Сведения о лице, имеющем право без доверенности действовать
       от имени юридического лица»: Фамилия/Имя/Отчество, Должность, Пол
       (если есть)
  5. Извлечённые данные показываются пользователю в интерфейсе для
     подтверждения/правки перед сохранением (не сохранять втихую — особенно
     важно для случаев автоматического склонения ФИО и определения пола).
  6. После подтверждения — данные сохраняются обратно в справочник УК ТЦ
     (см. раздел 3.2), чтобы при следующей генерации по этому же адресу
     запрос не повторялся.
- **Важное ограничение реализации**: никакого автоматического прохождения
  капчи, никакого скрапинга страницы поиска в обход капчи — это нарушает
  правила сайта ФНС и не должно быть реализовано ни в каком виде. Автоматизация
  касается только (а) подстановки ИНН в форму поиска и (б) разбора уже
  скачанного пользователем PDF.
- Тестовые данные для парсера — 3 файла в `examples/egrul_pdfs/`
  (ООО «СЕЛИНА», ООО «ДЭЛИКТ», ООО «ВИШЕНКА») — на них нужно проверить,
  что парсер стабильно находит нужные поля, несмотря на разное количество
  страниц выписки у разных организаций (структура полей в начале документа
  идентична, разница — в истории записей ЕГРЮЛ в конце, которая не нужна).
- Отдельный кейс, который парсер должен уметь распознавать и не ломаться
  на нём: если лицо, имеющее право действовать без доверенности, — не
  физлицо, а другая организация (управляющая компания). В этом случае
  вместо ФИО+пол в блоке будет название компании — приложение должно
  подставить его как есть, без попытки определить «Уважаемый/Уважаемая».

## 8. Генерация писем и реестр результатов

- Пользователь выбирает: сгенерировать все адреса из загруженной выгрузки
  объектов, либо выбрать подмножество (чекбоксами в списке/таблице).
- По каждому адресу-группе:
  1. Определяется название ТЦ и данные УК (справочник → при необходимости
     предлагается запустить проверку по ЕГРЮЛ, раздел 6).
  2. Формируется .docx по шаблону с подстановкой всех переменных полей.
  3. Файл сохраняется с именем по образцу существующих файлов (например,
     `улица_Барклая_дом_10А_ТЦ_Фили_05_08_2026.docx` — улица/адрес +
     (опционально) «ТЦ» + название + дата формирования).
- **Реестр (лог) генерации** — отдельная таблица/экран в приложении,
  показывающая по каждому запуску:
  - Всего адресов в пакете
  - Сколько писем сформировано автоматически (данные об УК были полные)
  - Сколько сформировано в обезличенном виде (без данных об УК/ИНН)
  - Сколько не удалось определить УК и требуют ручной проверки (включая
    edge-case с несколькими ИНН на один адрес, неоднозначные записи
    в справочнике, ошибки склонения ФИО, которые пользователь не подтвердил)
  - Список конкретных адресов по каждой категории (для навигации/повторной
    обработки)
- Реестр должен сохраняться между запусками приложения (например, в
  локальном файле/базе), чтобы накапливать историю, а не сбрасываться
  каждый раз.

## 9. Явные ограничения объёма (что НЕ автоматизируется)

- Автоматическое прохождение капчи на egrul.nalog.ru — не реализуется.
- Автоматический выбор между несколькими ИНН для одного адреса в
  справочнике УК ТЦ — не реализуется, только пометка на ручную проверку.
- Автоматическое разрешение противоречивых/неоднозначных записей в
  справочнике (например, запись-примечание об «отменённой» УК) — не
  реализуется, только пометка на ручную проверку.
- Заполнение последнего столбца таблицы-приложения («Торговая деятельность
  подтверждается/не подтверждается») — всегда оставляется пустым, для
  заполнения от руки.

## 11. Порядок работы (рекомендация для исполнителя)

1. Изучить все примеры в `examples/`.
2. Реализовать парсинг «сырой» выгрузки объектов + группировку по адресу
   (раздел 3.1) — проверить на прилагаемом файле.
3. Реализовать сопоставление со справочником УК ТЦ (раздел 3.2) — проверить
   на прилагаемом файле, включая нормализацию адресов.
4. Реализовать генерацию .docx по шаблону для обезличенного варианта
   (раздел 4.1.A) — простейший случай, сверить визуально с образцами
   пр-т Мира / 9-я Парковая.
5. Реализовать персональный вариант с адресатом (раздел 4.1.B), включая
   склонение ФИО и определение пола — сверить с образцами, где данные
   полные (Барклая 10А).
6. Реализовать расчёт даты срока с переносом на рабочий день (раздел 4.3).
7. Реализовать модуль ЕГРЮЛ (раздел 6) — на прилагаемых тестовых PDF.
8. Реализовать настройки (раздел 7) и реестр результатов (раздел 8).
9. Финальная сверка: сгенерировать письма по всем 9 адресам из образцов
   (используя реальные УК-данные, которые уже известны из справочника/
   образцов) и визуально сравнить каждое с оригиналом.
